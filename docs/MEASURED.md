## xcopy/robocopy 缓冲写穿透复测(`--io` 失效条件钉死)

日期:2026-10-26。语料 2008 文件 / 1086MB(8×128MB 大文件 + 2000×32KB 小文件),
源在 C:(SSD)且刚生成(全热在 64GB 缓存)。用户报告 xcopy/robocopy 限不住,复测证实。

**C:→C:(SSD,缓冲写)**:

| 档位 | 耗时 | 速率 |
|---|---|---|
| robocopy 基线 | 1.40s | 773 MB/s |
| robocopy `--io 30` | 1.33s | **814 MB/s(完全穿透)** |
| robocopy `--iops 100` | 4.56s | 238 MB/s(仅元数据被限) |
| robocopy `/J` 基线 | 2.18s | 497 MB/s |
| robocopy `/J --io 50` | 29.23s | **37 MB/s(精确压住)** |
| xcopy 基线 | 2.48s | 438 MB/s |
| xcopy `--io 30` | 2.15s | **506 MB/s(完全穿透)** |
| xcopy `--iops 100` | 5.25s | 207 MB/s(仅元数据被限) |

**C:→D:(HDD,缓冲写)**:基线 92 MB/s,`--io 20` 下 88 MB/s——拷贝期间完全没压住;
robocopy 退出后约 6s,D: 物理盘出现 52 MB/s 回写尖峰(1GB 脏数据由系统回写器全速刷盘,
Job 已无人)。对照 `/J --io 20` → 18-19 MB/s,精确压住,退出后无回写残留。

结论:

- **缓冲写的数据侧完全穿透 `--io`**:`WriteFile` 只进系统缓存即返回(无磁盘 IO 可限),
  落盘 IO 由内核 lazy writer 在系统上下文发出,不属于任何 Job。
- **`--iops` 只咬到元数据**:每文件 create/close 是同步操作、被计数,数据写在缓存完成,
  所以只把 773→238 MB/s(robocopy)、438→207 MB/s(xcopy)——温和减速,不是速率限制。
- **robocopy `/J`(无缓冲)让 `--io` 精确生效**(SSD 37 MB/s、HDD 18 MB/s,贴档位)。
  xcopy 无无缓冲模式,要么换 robocopy `/J`,要么 `--cpu` 节流阀。
- 2026-10-25 robocopy 一节测得 `--io 10` → 60 MB/s「可压」,与本次不矛盾:该轮语料
  是冷源,读侧同步 IO 被限拉低了整体;数据侧写穿透的结论以本节为准。
- 微软文档已标注 `SetIoRateControlInformationJobObject`「Windows 10 1607+: 不受支持」
  (功能仍在,官方不再维护,不要依赖它扩展)。

## 编排器 + burn/alloc(批量子代理风暴,树级三顶)

日期:2026-10-25。模拟 agent 编排器:`limit -- powershell 编排脚本`,脚本并行拉起
8 个子代理(burn/alloc),整棵树进同一个 Job 共享配额——对应「主 agent 一次派出
一批子 agent,每个子 agent 又有自己的工具进程」的真实形态。

**CPU 顶**(`--cpu 15%`,8 子代理 × burn 10s × 4 线程 = 32 线程打满 20T):

| 档位 | 树 CPU 时间(user+kernel) | 说明 |
|---|---|---|
| 基线 | ≈152s | 32 线程吃满整机,前台卡死 |
| `--cpu 15%` | 32.7s + 2.0s | ≈ 3 核 × 10s,精确压在配额上 ✅ |

**内存树顶**(`--mem-total 1G`,8 子代理 × alloc 512MB):

| 档位 | 树峰值 commit | 结果 |
|---|---|---|
| 基线 | 2728MB | 8×512MB 全部成功 |
| `--mem-total 1G` | 1074MB | 8 个子代理全部撞 1455 分配失败,树峰值压在配额内 ✅ |

**进程数顶**(`--procs 3`,编排器试图连拉 12 个子代理):

| 档位 | 放行/拒绝 |
|---|---|
| 基线 | 12 放行 / 0 拒绝 |
| `--procs 3` | 2 放行 / 10 拒绝(编排器自身占 1 席)✅ |

结论:子代理再多、再生孙子进程,CPU/内存/进程数都以**整棵树**为口径被摁在配额里;
`--procs` 对「编排器失控拉起子代理」(类 fork 炸弹)是硬闸。

## robocopy→HDD(10000 小文件,`--iops` 削峰保交互)

日期:2026-10-25。10000 个 4-64KB 小文件 / 327MB,C:(SSD)→F:(13T HDD 7200rpm),
robocopy 默认缓存写;采样 100ms 间隔的物理盘繁忙度/队列长度。

| 档位 | 耗时 | 盘繁忙度均值/峰值 | 队列峰值 |
|---|---|---|---|
| 基线 | 316.9s | 3% / **99%** | 5 |
| `--iops 60` | 316.8s | 2% / **64%** | 4 |

- 耗时几乎不变(316.9s→316.8s):HDD 小文件本身就被寻道压到 ≈1MB/s,IOPS 顶
  60/s 与磁盘自然节奏同量级,没有额外代价。
- 价值在**削峰**:基线期间盘繁忙度冲到 99%(整机 IO 卡顿的来源),`--iops 60`
  把峰值摁到 64%,同盘上的交互式操作(浏览/播放)不再被批量拷贝打爆。
- 与 7z/robocopy(C:)两节互证:缓存写负载的速率上限可用 `--cpu` 节流阀,
  而 HDD 场景的「保交互」需求由 `--iops` 直接管住操作数。

日期:2026-10-25。语料 17000 文件 / 660MB(C:→C:,SSD,默认缓存写)。

> 勘误(2026-10-26):本节 `--io`/`--iops` 的减速主要来自**冷源的读侧同步 IO** 被限;
> 缓冲写的数据侧写穿透(见上方复测一节)。本节数字保留作读侧限速的证据。

| 档位 | 耗时 | robocopy 报告速率 |
|---|---|---|
| 基线 | 6.3s | 112 MB/s |
| `--cpu 25%` | 9.6s | 73 MB/s |
| `--io 10` | 11.8s | 60 MB/s |
| `--iops 100` | 34.7s | 27 MB/s |
| `--iops 30` | 92.9s | 7.5 MB/s |

- 四类顶全部压得住,梯度与档位一致。
- **小数据量时 `--io`/`--iops` 无感**:78MB 同负载 `--io 10` 完全不减速——拷贝全进
  文件缓存,IO 限速 API 管不到回写。数据量上去(缓存压力)后才拉开差距。
- `--iops` 对 robocopy 很灵敏:每文件 create/read/write/close 全计数,30 IOPS
  压到 7.5MB/s(15 倍减速)。机械盘上给 robocopy 限速保交互,`--iops` 优于 `--io`。
- robocopy 退出码 1 =「有文件被拷贝」,是正常返回码,不是报错。

## 7z(解压,缓存写 + 吃 CPU)

日期:2026-10-24。两组负载。

**小包**:388MB → 396MB 输出,全部进文件缓存(回写未发生):

| 档位 | 耗时 |
|---|---|
| 基线 | 1.57s |
| `--cpu 10%` | 1.80s |
| `--cpu 5%` | 2.46s |
| `--cpu 2.5%` | 7.96s |

**大包**:2GB 压缩包 → 解压 7.5GB / 5.7 万文件到 F:(HDD),跑完整程:

- 基线全程 2130s ≈ 3.6MB/s;物理写入除开头外稳在 4MB/s(机械盘小文件底盘)。
- 开头有 61MB/s 的缓存回写爆发;`--cpu 5%` 把爆发削到 13MB/s,曲线全程平稳
  (`10%` 也有 62MB/s 突刺)。

结论:`--cpu` 是「全 IO 类型」节流阀,实际 IO 速率 ≈ min(磁盘自然速率, CPU 顶折算速率);
吞吐压无可压时(HDD 小文件),价值在削峰。

## `--iops` 的 8KB 归一化口径 与 `--ops`(真实操作数)校准

日期:2026-10-26。起因:用户问「`--iops 300` 拷大文件为什么只有 3MB/s」。

### 根因(微软文档 + 实测)

`JOBOBJECT_IO_RATE_CONTROL_INFORMATION.BaseIoSize` 是「归一化 IO 单位」的基数,
默认 8192 字节:**每 8192 字节算 1 个 I/O unit**(8000 字节算 1 个,8001 算 2 个)。
所以内核数的是「按 8KB 折算的 unit 数」,不是真实操作次数。文档明确:
`SetIoRateControlInformationJobObject` **要求 BaseIoSize 传 0**,唯一可改途径是整机注册表
`HKLM\SYSTEM\CurrentControlSet\Control\QoS\StorageBaseIOSize`(需管理员+重启;本机该键不存在 → 默认 8192)。
另:Job 自带的 `IoInfo` 计数器实测恒为 0,真实操作数只能逐进程 `GetProcessIoCounters` 取。

### 证据(裸 IO 探针,无缓冲直写,绕开缓存;D 盘 HDD)

固定 32MB 总量、`--iops 300`:

| 块大小 | 速度 | 折算真实 ops/s |
|---|---|---|
| 4KB | 0.56 MB/s | 138 |
| 8KB | 1.15 MB/s | 140 |
| 64KB | 2.23 MB/s | 34 |
| 128KB–4MB | **2.4–2.6 MB/s(封顶)** | — |

平台期 = 300×8KB/s。**顺序读与随机读在限速下完全相同**(4KB: 6.07s vs 6.01s),
证明计数器不看寻道——IOPS 顶不是寻道计数器。

### 附:曾经尝试过的 `--ops`(已废弃)

一度实现过 `--ops`(用 `GetProcessIoCounters` 测真实操作数,再反算内核 MaxIops),
但实测发现它的口径仍是「IO 次数」而非「寻道」——顺序写 1MB 与随机读 4KB 被同等对待,
对「限制寻道频率」这个真实需求没有意义,且校准存在系统性欠速(目标 50 实测 13~34)。
已移除,由 `--seeks` 取代。保留此段仅为记录踩过的坑。

关键教训:
- **每次 `SetIoRateControl` 都会重置令牌桶**:同一 MaxIops=100,设一次 11.1 ops/s,
  每 250ms 重设一次 55.5 ops/s(5 倍)。所以任何「持续伺服」的校准方案都会让限速失效。
- `GetProcessIoCounters` 的 other 计数含大量零字节元数据操作,计入会让实测速率虚高 13 倍。
- 顺序大块 IO 的进程级操作数会被内核合并(2000 次写只报 56 次),**不能代表寻道**。

## `--seeks`:按「寻道频率」限速(2026-10-26 提出,2026-10-27 重写)

动机只有一个:**面向 HDD 保护磁头**。大文件的事务密度低(2GB 只 ~1000 次事务),
小文件的事务密度极高(250MB/4000 文件 ~9700 次),所以「限设备层事务数/s」天然
对大文件松、对小文件狠。此外 src / dst **任一盘超目标都要压**。

### 为什么「设备层事务数」能代表寻道

同 2000 次真实 IO,D: (HDD) 实测(进程级 `GetProcessIoCounters` vs 设备层 PDH):

| 负载 | 进程 IO op/s | 设备层 transfers/s |
|---|---|---|
| 顺序写 1MB | 3 | 277 |
| 顺序写 64KB | 130 | 478 |
| 随机读 4KB | 5579 | 2329 |

顺序大块被内核合并,进程计数只有 3 op/s;随机 4KB 是 5579。**只有设备层
`Disk Transfers/sec` 随随机性单调上升**,它是寻道频率的可用代理。

### 实现(重写版)

- **测量**:`\PhysicalDisk(*)\Disk Transfers/sec` 通配符计数器 + `PdhGetRawCounterArrayW`
  读**每个物理盘实例**的累积原始值,按实例名(`1 D:` / `2 E: F:`)匹配盘符。
  同一物理盘被多个盘符命中只算一次——旧版用 `*d:*` 通配符逐盘加计数器,
  同盘多盘符会重复计数。免管理员(已验证)。
- **多盘**:`--seeks N D: E:` 或 `--seeks N all`;每盘独立记账,**任一盘超目标**
  就冻结整棵进程树。这就是「src/dst 谁超标谁触发」。
- **控制律**:20ms 采样 → 每盘 欠账 = 观测事务数 − 目标×dt → 按 `欠账/目标` 分块冻结
  (5ms..250ms),每冻完一块立刻复采样,直到欠账清零。旧版是 100ms 采样 + 单 tick
  最多冻 90%,削减上限钉死在 10 倍(目标 50 实测 735/s,根本压不住)。
- **冻结句柄缓存**(300ms 刷新):旧版每次冻结/恢复都做一次全进程表快照 + `IsProcessInJob`,
  100 轮/秒时开销爆炸,这也是当初不敢把采样调细的原因。
- **报告修正**:整段均值 = 总事务/总耗时(旧版对 100ms 瞬时采样取平均,系统性偏高;
  短命令样本为 0 时还直接打印 `0/s`),并给出冻结占空比。

### 实测(2026-10-27,D: 4TB / E: 12TB 均为 7200rpm SATA HDD,robocopy `/J` 无缓冲)

**4000 个 64KB 小文件,D:→E:(250MB)**:

| 档位 | 耗时 | E: 实测均值 | 冻结占空比 |
|---|---|---|---|
| 基线(不限) | 14.3s | 681/s | 0% |
| `--seeks 200 D: E:` | 51.9s(×3.6) | 189/s | 73.6% |
| `--seeks 100 D: E:` | 99.3s(×6.9) | 97/s | 85.0% |

**2GB 单文件,D:→E:**:

| 档位 | 耗时 | 事务总数 | E: 实测均值 | 冻结占空比 |
|---|---|---|---|---|
| 基线(不限) | 12.6s(163MB/s) | 2075 | 165/s | 0% |
| `--seeks 200 D: E:` | 12.3s(**无影响**) | 2050 | 167/s | 9.9% |
| `--seeks 100 D: E:` | 21.3s(×1.7) | 2108 | 99/s | 95.4% |

结论:

- **同一档位,小文件与大文件的代价完全不同**:100/s 下小文件慢 6.9 倍、大文件只慢 1.7 倍。
  根因是事务密度:小文件 9762 事务/250MB ≈ 39,000 事务/GB,大文件 2075/2GB ≈ 1,040 事务/GB(差 37 倍)。
- **200/s 一档大文件零影响**:该负载自然事务率 165/s 本就低于目标,控制器几乎不冻结(占空比 9.9%)。
- **任意一盘超标即触发**:小文件 200 档里 D: 只有 80/s(未超标)、E: 189/s 触发压制,D: 顺带被冻到 80/s 以下——
  冻结不分盘,这是占空比式限流的固有代价。
- **控制精度**:目标 200 → 189/s,目标 100 → 97/s(旧版目标 50 → 735/s)。
- **吞吐天花板 ≈ 目标 × 平均 IO 大小**:100/s ⇒ 4KB 随机 ≈0.4MB/s、64KB ≈6MB/s、1MB 顺序 ≈100MB/s。
  所以目标值要按「能接受的顺序吞吐」倒推,而不是按「盘标称 IOPS」。
- 事务总数几乎不变(9762→9810、2075→2108):限的是**速率**不是丢 IO,只是把同样的工作拉长。

### 已知边界

- 计数器是**整盘**口径:同盘其他程序的 IO 也计入,无法区分是谁造成的。背景负载本身
  高于目标时,本程序会被自己的控制律饿住(占空比拉满,打印一次告警)。
- 冻结作用于整棵树、不分盘:一盘超标时另一盘的 IO 也一起停。
- 该负载在 SSD 上会被 64GB 内存高速缓存吃掉(实测 2000 次随机 4KB 读 0.01s 完成、设备事务 0)。
  **验证 `--seeks` 必须用 robocopy `/J` 之类无缓冲写,或远大于缓存的冷数据**,否则测到的是内存。

### 怎么选目标

先跑一遍 `--seeks 1000000 D:` 看该负载的自然事务率(日志里的「均值 N/s」),
取 `自然值 / 2 ~ / 3` 通常就是「明显不卡机器、但活还能干」的档位。

### 逐 IO 偏移量(ETW Kernel-File)为什么没做

`StartTrace` 实测需管理员(ERROR_ACCESS_DENIED),与「只要管理员身份才需要」的项目原则冲突
(见 README 设计取向),故用设备层事务率作为等价目标。
